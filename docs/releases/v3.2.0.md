# Homebox Companion v3.2.0 — release candidate

This candidate brings the unreleased development work since v3.1.1 into main.
It is not a published release.

## Inventory capture and review

- Preserve compressed photos when confirming an unchanged review item. Replace
  cached compression only when the photo list changes, avoiding unnecessary large
  uploads while keeping edited images correct.
- Isolate analysis runs so cancelled or superseded work cannot overwrite a newer
  scan. Clean up camera streams, object URLs, timers, subscriptions, and pending
  editor or picker requests when their owner closes or navigates away.
- Preserve custom fields through review persistence and recovery. Improve custom
  field extraction instructions and keep a selected container/location when
  creating items with extended fields.
- Improve location navigation, recovery, and page/service ownership to keep
  asynchronous responses scoped to the current scan, collection, and session.

## Authentication and chat

- Preserve recoverable scan state through reauthentication and ignore stale
  refresh/request results after logout, account changes, or collection changes.
- Prevent overlapping messages, approvals, rejection, and history clearing within
  a chat session. Conflicting operations return HTTP 409. Claim each approved
  action once so retries cannot execute the same queued action twice.
- Keep valid tool-result history when streaming is interrupted and use the
  active application's chat configuration.

## Settings and backend reliability

- Write settings atomically, serialize in-process reads/writes, and validate LLM
  profile status and primary/fallback invariants before saving.
- Fail explicitly when an existing settings file is empty, malformed, or invalid,
  instead of silently falling back to environment defaults. Avoid exposing saved
  secrets in settings-parser diagnostics.
- Honor per-application upload, image-quality, printing, and request configuration.
  Run image compression off the event loop with a shared concurrency budget that
  remains occupied until cancelled requests' worker threads finish.
- Improve Homebox transport cleanup, request errors, and partial item-creation
  handling.

## Interface and tooling

- Improve shared dialog keyboard/focus behavior, accessible names, scroll locking,
  touch targets, reduced-motion support, and consistent styling/design tokens.
- Retain the completed Tailwind CSS 4, TypeScript 6, Node 26.10.0,
  prettier-plugin-svelte 4, and Lucide 1 migrations. Refresh compatible frontend
  and Python dependencies and add focused lifecycle, recovery, and visual tests.
- Validate pull requests and main/dev pushes, including a real browser → Companion
  → disposable Homebox scan and AMD64/ARM64 container builds without publishing.
  Container publishing now depends on the same validation suite at the selected
  tag/ref.

## Upgrade and compatibility notes

- Back up the persistent data directory (especially `settings.yaml`) before
  upgrading. A previously ignored invalid file can now prevent startup; inspect
  and repair or restore it rather than expecting environment fallback.
- Fresh configurations default to `gpt-5.6-luna`. Existing saved model profiles
  retain their model selection. Configure `HBC_LLM_MODEL` or a saved profile for
  the provider/model available to your account; the credential-free CI suites
  do not verify real provider access or the published cost benchmark.
- The Tailwind 4 interface targets Safari 16.4+, Chrome 111+, and Firefox 128+.
  Older browsers are outside this candidate's supported CSS baseline.
- Source builds use Python 3.14+ and Node 26.10.0. Container deployments receive
  those runtimes in the image and do not require host Node/Python upgrades.
- Settings locking and chat claims are process-local. The supplied single-process
  container is the supported deployment shape; this candidate does not establish
  safe shared-state behavior across multiple worker processes.

## Release procedure

1. Require all candidate PR checks to pass, including the full-stack journey and
   both container architectures. Merge with a merge commit (avoid squashing or
   rebasing away the preserved dev/main ancestry).
2. Wait for the Validate run on the resulting main commit to succeed. If main
   changes, validate the new intended release commit again before tagging.
3. Tag that validated commit as `v3.2.0` and publish only then. The publishing
   workflow revalidates the selected tag before it can push an image. No tag,
   release, or container has been published as part of preparing this candidate.
